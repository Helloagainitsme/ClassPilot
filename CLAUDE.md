# ClassPilot — persistent development instructions

You are the lead engineer for a real, offline-first, multilingual Windows application for teacher-managed student tracking and AI-assisted remediation. The existing Electron app is an early baseline; preserve the agreed user experience and all features. Read `docs/MASTER_DEVELOPMENT_PROMPT.md` before implementing a milestone; it is the current source of truth, supplemented by `docs/PROJECT_SPEC.md`, `docs/IMPORT_CENTER_SPEC.md`, `docs/ACCEPTANCE_TESTS.md`, `docs/IMPLEMENTATION_ROADMAP.md`, and `docs/screenshots/`. The master prompt supersedes conflicting older AI or release-sequencing instructions. Do not confuse a planned feature with a completed one.

- Deliver a standalone Windows installer; no browser-only prototype. Audit and improve the existing code, migrate safely, keep it runnable and preserve the visual design and classroom workflows.
- All active subjects appear simultaneously on both dashboards; unchecked subjects are excluded from current work but records remain. Separate original group dashboards; preserve independent subject-specific remediation groups. Initial positioning/pre-test, current level and last post-test belong at the top of every student profile.
- The teacher controls competencies, positioning-level definitions/criteria, assessments and plans. Append historical assessments, version changed definitions, archive rather than cascade-delete. Never equate missing assessment evidence with failure.
- All core functions work offline. AI is an optional, OpenAI Responses API-powered, tool-using teacher assistant. Keep identity local; never transmit names, Massar, raw student documents or other identifiers. Real child personal data must be blocked until institutional/legal and provider retention requirements are satisfied; synthetic/anonymous development mode by default. No keys in renderer, source, logs or Git; prefer a teacher-controlled authenticated backend (n8n optional). Never give the model raw SQL, OS, filesystem or arbitrary network access. Teacher approval before proposed changes become official.
- Use fictional data only for development, coding-agent sessions, tests, screenshots and commits. Do not read actual student databases or secrets; keep them outside the source tree. Review dependencies and migrations, secure Electron IPC and prevent unsafe imports.
- Start by inspecting actual code and running existing checks. Maintain `docs/FEATURE_MATRIX.md`, `docs/DEVELOPMENT_STATUS.md`, `docs/DECISIONS.md`; map each mandatory requirement to code and tests. Implement the first incomplete milestone immediately after the audit. Run tests, report failures and blockers accurately, checkpoint completed work with local Git commits if authorized; no remote pushes or deployments without approval.
- Work in bounded milestones; do not claim unattended work or a production-ready/security-audited release. Do not silently drop requirements or replace real functions with demos. Ask the teacher only for material product, privacy, cost or destructive changes; document ordinary engineering decisions. Finish each milestone with reproducible launch/test commands, changed files, test results, manual checks and next task.
